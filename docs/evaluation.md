# 产品评估与适用题型（2026-11-12，v0.3.2 时点）

> 基于通宵真人手操实测（10 样本全链路）+ 与作者讨论后的定位结论。
> 工具迭代后本文相应更新；评估口径是「对 CTF 逆向做题者」。

---

## 一句话定位

**它不是「更好的 Ghidra」，而是「Ghidra 的 CTF 做题前端」——把做题时在 IDA/Ghidra/杂牌工具间来回横跳的动作，压缩进一个页面。**

判断口诀：**密文在文件里、算法看得懂 → 用它；答案在运行时 → 还得开 gdb。**

---

## 强项（真实差异化）

| 维度 | 评价 |
|---|---|
| **做题链联动** | 核心价值所在。查壳结论 → 字符串锚点 → xref → 反编译精确行高亮，这条链照真实解题心智路径设计，Cutter/Ghidra 原生都没有这种串联。实测双击字符串直接落到目标 `printf` 行 |
| **CTF 特化** | 解码实验室（链式 + XOR 爆破 + 已知明文推 key）、常量扫描（40+ 签名、大小端自动、归属函数）、PyInstaller 解包闭环——CTF 高频动作，通用工具不管 |
| **零依赖哲学** | 除 pyghidra 外 stdlib 手写，前端原生 JS。离线可用、审计容易、贡献门槛低 |
| **上手成本** | 对比 Ghidra（Java/Swing）和 Cutter（C++/Qt 构建地狱），pip install + 浏览器的部署/贡献成本低一个量级 |

## 短板（诚实版）

| 维度 | 现状 | 差距 |
|---|---|---|
| **动态分析 = 0** | 无调试、无 patch、无模拟执行 | 做题一半的场景（反调试、动态 dump、随机密钥）覆盖不了 |
| **静态深度不足** | 无结构体/类型编辑、无 FIDL 签名库、反编译选项不可调 | 重度逆向还是得回 Ghidra/IDA 本体 |
| **引擎天花板** | 反编译质量 = Ghidra 12.2 | 对混淆/花指令没有额外解法 |
| **规模边界** | 4047 函数（ez_debug）验证过；10 万函数级固件未测 | 未知区 |
| **单人架构** | 引擎单 worker 线程串行化 | 多样本并行分析做不到 |
| **发布成熟度** | 未上 PyPI，无贡献者文档、无 demo GIF | 开源传播未启动 |

## 竞争格局

- 对 **Ghidra 用户**：价值 = 省掉写 GhidraScript 的摩擦；但 Ghidra 脚本生态巨大
- 对 **IDA 用户**：差距主要在交互打磨年限和 F5 反编译质量
- 对 **Cutter / ImHex**：Cutter 功能全但重；ImHex 的 Pattern Language 是数据解析的降维打击（已列入路线图）
- **AI 时代定位**：刻意无 AI 是差异化——代价是功能面必须靠「顺手」赢，目前这个「顺手」只在做题链一处成立

## 工程健康度：B+

- ✅ 测试纪律（125 个）、文档习惯（dev-notes 踩坑 #1–#15）、发版节奏、错误路径处理（锁泄漏、坏样本、路径遍历防护）
- ⚠️ 已知债：pytest 引擎测试偶发 JVM 挂起、`server/app.py` 539 行、前端 app.js 2200+ 行无模块拆分、Windows 之外零验证

## 投入性价比排序

1. **gdb 桥**（动态做题链）——补最大空白，"断点偷内存 → 送解码实验室"链路现成
2. **PyPI + demo GIF**——让「存在」变成「可安装」，成本一下午
3. **Pattern Language 轻量版**——CTF 解结构数据刚需
4. **结构体/类型编辑**——决定它是「查看器」还是「工作台」的分水岭

## 适用题型（用作者真题划档）

### 甜蜜区——工具显著加速，甚至半自动出 flag

| 题型 | 实测样本 | 工具角色 |
|---|---|---|
| 异或/编码链 crackme | ez_debug（^0x17 + "ATRI" + base64 密文） | 最甜：查壳 → 字符串锚点 → 读算法 → 解码实验室直接出 flag |
| 标准算法识别 | c_sm4（国密） | 常量扫描一眼定位 S-box @ 函数；解密脚本自己写 |
| Python 打包 | pyre | 一键解包 + 入口 pyc 路径复制；pyc→源码交给 PyLingual/pycdc |
| 简单前缀/查表比较 | crackme 1337（ARM）、`ord(c)*33%179` | 反编译直读逻辑，ARM 由 Ghidra 引擎兜底 |
| 未知样本预处理 | 任意 exe | 查壳结论决定「走静态还是上脱壳」的第一步 |

**共同特征：密文写死在程序里、算法可读、答案静态可算**——CTF 逆向新手到中段的主力题型。

### 能用，但工具只当「看」的底座

| 题型 | 样本 | 现状 |
|---|---|---|
| 逻辑模拟/迷宫 | MazE | 反编译+调用图帮读状态机，「走」靠人写脚本 |
| 自定义 VM / opcode | FunPyVM、opcode.bin | 提供反汇编底座与字符串锚点，VM 语义还原手工 |
| 花指令/轻度混淆 | flower（685 函数） | 能打开能看，无去花指令辅助，费劲程度同 IDA |

### 不适合（直接开别的工具）

| 题型 | 样本 | 原因 |
|---|---|---|
| 动态调试刚需 | Random Crackme（随机密钥 + ptrace 反调试） | 答案运行时才生成，需 gdb |
| 溢出/利用 | ExploitMe | 需 debugger + fuzz，出圈 |
| 魔改壳脱壳 | Ferris（Cha0/Cha1 自定义 UPX-LZMA） | 能识别「疑似加壳」，脱壳要手脱 |
| 反编译对抗 | 混淆 pyc、VMP | 超出引擎天花板 |
